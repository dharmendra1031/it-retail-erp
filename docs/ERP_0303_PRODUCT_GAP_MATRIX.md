## Database and API findings

EF `ApplicationDbContext.cs` configures unique SKU and filtered non-null barcode indexes, restrictive Category/Brand/Unit FKs, three-decimal prices and six-decimal reorder; the EF Product migration creates `BIGINT IDENTITY` and NVARCHAR bilingual columns. Django `catalog/models.py` and `0002_product.py` define the equivalent `BigAutoField`, protected FKs, unique identifiers and decimal dimensions. The physical Django SQL Server index/filter behavior and full upgrade/rollback parity still require ERP-0310/0319 test evidence. No schema change is justified by this comparison alone.

Product create/update have a check-then-save race in both backends. The database uniqueness constraint preserves committed identifier uniqueness, but the ASP.NET API can return an unhandled SQL exception on a racing duplicate; the Django fallback returns a generic 400 rather than its preflight field error. The exact response parity and no-partial-write result require the dedicated concurrent SQL tests in WP16. Product delete uses hard delete; later stock/sales foreign keys and immutable financial audit are owned by their transaction/audit packages, not this master-data gap step.

**ERP-0303 result:** requirement gaps are recorded with current source paths and assigned owners. No Product runtime behavior, schema, migration or acceptance status changed. Next ERP-0304 specifies the bilingual stock-product happy path.
