# ERP-0306 — Product Master data and configuration design

**Scope:** WP16 Product/Item Master, SRS §§4, 12–14, 42–43 as extracted in `SRS_BASELINE.md` and `ERP_0301_PRODUCT_SCOPE.md`. Reviewed `development` at `3caddebd46b00a52855ba88fae45b371a553776c`. The original linked SRS was not accessible for a fresh revision check. This design records what is safe to retain now and which business decisions must precede an additive schema change; it is not approval of an unchosen policy or a migration.

## Current persisted contract

| Concern | Current SQL design in ASP.NET / Django | Design decision for WP16 |
| --- | --- | --- |
| Primary identity | EF `Product.Id` is `long` mapped by `20261023140000_Products` to `BIGINT IDENTITY(1,1)`; Django `Product.id` is `BigAutoField` in `0002_product`. | Keep one numeric, server-generated Product ID. API returns JSON number; no GUID or user-entered primary key. |
| SKU / Item Code | `Sku`/`sku` is required, max 40, unique; both APIs trim and uppercase ASCII SKU. No separate Item Code exists. | Keep unique normalized SKU as the current business key. Do not silently alias an independent Item Code. Resolve decision D1 below before adding `ItemCode` or changing labels/contracts. |
| Barcode | Nullable max 64, unique. EF uses a filtered `Barcode IS NOT NULL` unique index; Django uses `unique=True, null=True` and needs physical SQL Server index proof. Both APIs trim/uppercase nonblank values. | Retain optional barcode and one canonical uppercase value. No global scan-to-cart or label behavior in WP16; WP31/WP45 own those actions. |
| English/Arabic text | Separate `NameEn/NameAr` max 200 and `DescriptionEn/DescriptionAr` max 1000; EF migration uses NVARCHAR, Django uses Unicode-capable CharField through SQL Server backend. | Preserve both languages as distinct fields, no transliteration. English name required in current API; Arabic name/description remain optional until an explicit completeness policy is chosen. Verify Unicode round-trip. |
| Classification | Required Category and Unit BIGINT FKs; optional Brand BIGINT FK; EF Restrict, Django PROTECT. Category already has parent hierarchy. | Require active Category/Unit, optional active Brand under current contract. Leaf-only Category and mandatory Brand rules remain D2; never infer them from `parent_id` alone. |
| Product type | `stock`, `nonstock`, `digital`; `SerialTracked` boolean. | Retain type vocabulary. WP16 rejects stock-only settings on nonstock/digital; WP17 owns type-specific transaction/license data, WP22/23 serial and warranty lifecycle. |
| Prices | `CostPrice`, `BasePrice`, `MinPrice` / snake-case equivalents use DECIMAL(18,3); API accepts decimal strings and emits fixed-point strings. | Retain exact three-decimal nonnegative values, reject excess scale and `minPrice > basePrice`; no float calculation. Meaning of separate Purchase Price and standard retail price is D3. Wholesale/multi-price policy is WP20. |
| Tax | No Product tax category, rate, exemption or tax-inclusive flag; no tax configuration table is yet owned by WP16. | Do not hard-code Kuwait tax or add an arbitrary rate column. WP18 owns configurable tax engine. Product-to-tax-category linkage must be designed with WP18's category model and effective-date rules (D4). |
| Reorder / quantity | `ReorderLevel` DECIMAL(18,6), nonnegative; no Product opening/current quantity column. Unit has `decimalPlaces` 0–6. | Retain reorder threshold. Stock balance is derived from ledger movements in WP21/WP25, with unit precision enforced by posting logic. Never edit a Product quantity to post stock. |
| Status / timestamps | `IsActive` boolean; created/updated UTC timestamps in both models. | Retain active/inactive master status. Future purchase/sales posting rejects inactive Product at transaction time; use UTC storage and localize only presentation. Transaction document statuses are separate. |

## Open Product policy decisions and safe alternatives

- **D1 — Item Code vs SKU (WP16):** If the SRS uses two labels for one identifier, show one normalized `sku` in API/storage and decide the UI label. If Item Code is a separate identifier, add a nullable unique `ItemCode`/`item_code` to both backends in a forward migration, backfill only with an approved mapping, then make it required only after data review. Do not synthesize duplicate codes from existing IDs or silently reinterpret SKU.
- **D2 — Product classification (WP16):** Current Category FK can point to a root or child, and Brand is optional. If only leaf categories are saleable, validate that rule in both APIs and revalidate on category-tree changes; do not introduce a redundant `SubcategoryId` while Category already has `ParentId`. If Brand becomes mandatory for selected types, define those types first and validate per type. Existing records need an upgrade plan before adding NOT NULL constraints.
- **D3 — Price semantics (WP16/WP20/WP24):** Current `costPrice` can represent one master reference cost and `basePrice` one standard selling price. If Purchase Price must be distinct from landed/weighted cost, define its source and update rule before adding a second DECIMAL(18,3) column. Wholesale or customer-specific prices should use WP20 price lists rather than a guessed Product column. No price may be computed with binary floating point.
- **D4 — Tax linkage (WP18 with WP16 contract):** A future Product tax-category FK should reference configurable tax categories, not a hard-coded percentage. Decide exemption, effective dates, tax-inclusive pricing and posted-document rate snapshots in WP18; a later additive migration can link Product to that model. No current Product rate is assumed.
- **D5 — Model and warranty (WP16/WP23):** If device `Model` is a searchable master attribute, add an optional Unicode field with an agreed length and backfill policy in WP16. A warranty period must be attached to the approved Product/serial/invoice relationship designed in WP23, rather than inventing a Product integer now.

These alternatives are decision gates for the owning implementation step, not claims that the owner selected an answer. WP16 can still build and test current core Product fields and search while the ambiguous extra fields remain explicit. Before closing WP16, resolve every field that the approved SRS requires in Product Master; an unresolved owner decision cannot be treated as implemented.

## Migration and verification plan

**ERP-0306 schema action: N/A.** Existing EF and Django Product migrations already represent the current core contract; this design changes no runtime field, API or persistence rule. Generating an empty migration would provide no safety evidence. ERP-0310 must inspect the physical SQL Server schema for both implementations, migration parity, unique barcode behavior with multiple NULL values, restrictive FKs and rollback implications.

For any approved new WP16 field, make a forward-only additive migration in both backends. Start nullable/default-safe when existing rows need a decision, backfill under a reviewed data migration, add/check uniqueness and NOT NULL only after duplicate/null audit, and test upgrade from the preceding version plus a safe disposable rollback. Preserve `BIGINT` IDs, Unicode, exact DECIMAL scale, existing product rows and API compatibility. Do not run a destructive rollback on production. Product write atomicity, unique-constraint race mapping and no-partial-write proof belong ERP-0312–0313/0319; persistent audit belongs WP46. No production data or schema was accessed for this design step.
